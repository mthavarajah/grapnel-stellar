# Hyperliquid execution adapter — offline implementation only

Implements the lead-owned `modules/perpetuals/execution-contract.ts` without changing routes, shared contracts, database, runtime, catalog or UI. No live HTTP transport is supplied; no exchange request, wallet/account creation, funding/deposit/cancel/close, mainnet request or real signing credential was used. All positive execution results in tests are explicitly injected offline fixtures, not financial proof. Trading is **not ready**.

## Integration

Construct `HyperliquidTestnetExecutionAdapter` with a fixed exact `BoundPerpetualAccount` scope and the injected interfaces exported from `types.ts`:

- `transport.rpc/info` return `{endpoint,request,receivedAt,body}`. Endpoints are fixed Testnet RPC, `/info`, `/exchange`; receipts must match the exact requested endpoint/body and be at most five seconds old. RPC must return chain998. There is no environment URL override or default network client.
- `verifyCustomerApproval(intent,account)` independently verifies the exact customer approval. `verifyAccountExecutionProof(account)` independently verifies eligibility, attributed actual funding and current provider execution proof. Missing verifiers fail closed before signing. These are trusted server integrations, never browser/body booleans or API-key spend authority.
- `resolveSigner(signingKeyRef)` supplies a typed-data wallet with the **same public EVM address as the trading account**. Delegated agents, vaults and shared customer accounts are unsupported. No private key belongs in this adapter, artifact or logs; signer failures are sanitized.
- `durability.reserveIntent` atomically reserves account nonce/client-order-ID and operation uniqueness before signing, globally across workers. `prepare` returns a serializable `SignedPerpetualAction`; the caller must persist its **entire exact payload**. `loadPrepared(operationId,intentHash)` must enforce this configured tenant/customer/wallet scope and return that immutable server-owned record. `claimSend` performs a durable atomic compare-and-set before the exchange call. It must never reset after an uncertain result. The adapter never generates a replacement nonce or client ID.

The send claim precedes the final fresh position/metadata check. If that check fails, no exchange call occurs, and the claim remains consumed. A new separately approved intent is required; do not clear the claim or blindly retry the old action. Repeated send claims reconcile only. Expired actions reconcile without transmission. Reconciliation does not require a fresh customer approval because it observes an already stored operation; root routes must still enforce caller tenant/customer authorization before adapter access.

## Signing and order scope

Pinned SDK `@nktkas/hyperliquid@0.33.3` supplies `canonicalize(OrderRequest.entries.action, ...)`, `signL1Action` and `createL1ActionHash`. L1 order signatures use EIP712 **Exchange / version1 / chainId1337 / zero verifying contract**, Agent `source:"b"` for Testnet. This is distinct from the separate **HyperEVM chain998** network check. Source signature recovery is independently checked using pinned `viem@2.57.18`; wrong account/domain/source or mutated action/nonce/expiry fails.

One exact IOC limit order, grouping `na`, no builder fee, no vault, no trigger or leverage update. Exact positive decimal strings and bigint calculations only. Size must fit metadata `szDecimals`; price must already fit the five-significant-figure and `6-szDecimals` perp rules, with the documented integer-price exception. Input is never rounded. Nonce must be within sixty seconds and expiry no later than nonce+sixty seconds. Current configured leverage must already match the approved leverage; the adapter never changes it. Close requires reduce-only, the opposite side and size no larger than the actual current position; a non-reduce opposite-side order is rejected.

Execution allowlist is native and `xyz` with USDC collateral only. Builder index is read from fresh `perpDexs`; global ID is `100000 + actualDexIndex*10000 + localIndex`, and exact qualified symbol/DEX/index/metadata are checked. Other discovered DEXes/collateral types remain blocked; this does not limit the catalog reader's wider discovery.

Both `hyperliquid-testnet:perps:<globalIndex>` and `hyperliquid-testnet:stocks:<globalIndex>` are supported internal IDs. **Stocks aliases additionally require `verifyStockMarketCategory(identity)`** returning fresh exact `{network,assetIndex,providerSymbol,dex,category:"equity"|"index",observedAt}` from the lead's trusted source classification. Missing, stale, crypto, mismatched or body-derived classification must not pass. This adapter has no ticker heuristic and does not describe these perpetuals as shares.

## Settlement evidence

Exchange acknowledgement is ignored as completion proof. Even after timeout the only next action is reconciliation by the persisted cloid. Require matching `orderStatus` identity (coin, side, limit, original size, cloid, reduce-only, timestamps), source fills and the actual account position. Fill IDs must be unique real provider IDs; hashes, size/price/time and order ID must validate. Each fill's `startPosition` must causally chain from the prepared baseline to the actual final position. Other same-asset fills, duplicates, mismatched accounts/assets, price-bound violations or incomplete/capped data remain unknown. A result at or above the source2000-fill page cap requires pagination outside this implementation and cannot prove completion here.

Full filled state requires full approved size and matching actual delta. Partial IOC execution returns `cancelled` **with nonzero actual `filledSize`, average and fill IDs**; root must display/reconcile that remaining position and must not treat it as no execution. Zero-fill IOC cancellation is `no_fill`, not completed trading. Nonterminal IOC/resting/GTC states remain unknown. For unknown evidence, zero/empty fields mean **unverified**, not a claim of no execution or zero customer balance; root must retain the pending/uncertain operation and read actual positions before any new attempt. Weighted execution average uses bigint arithmetic, truncated at eighteen decimal places; fill prices and order inputs are never rounded. No maximum implicit venue fee exists in the frozen intent; the adapter adds no builder fee and makes no claim that a venue fee cap was approved.

## Browser-held customer EVM signing extension

`prepareCustomer(intent, boundAccount): Promise<UnsignedPerpetualAction>` validates the configured exact scope, fresh sixty-second intent, fresh source market/current leverage/position, access/funding readiness and atomic nonce/cloid reservation. It **does not invoke customer-approval verification or a server signer**. The returned JSON-safe object has the existing outer action fields plus **top-level `typedData`**, and payload `{version:1,intent,account,market,before,wire:{action,nonce,expiresAfter}}`; signature is absent. The exact EIP712 data is reconstructed from the pinned SDK L1 hash/domain1337/sourceb and includes expiry. `inspectUnsignedArtifact(unsigned, scope)` is exported for persistence validation.

Root must save that entire immutable unsigned request, send only the approval display/typed data to the browser, and later load the server-owned request by scoped operation ID. Never accept browser-provided intent/account/baseline/typed data as the server request. `authorizeCustomer(rootLoadedUnsigned, signatureHex)` validates the exact reconstructed unsigned fields, fresh customer approval/access/funding proof, standard65-byte EVM signature/recovered account and fresh unchanged baseline/market/leverage. It returns the existing signed action, **drops top-level typedData**, and adds only `payload.wire.signature`. It neither signs on the server nor sends an order. `resolveSigner` is optional for this browser path; the old `prepare` still requires it. No key/ref secret is needed in the browser flow; `customer-wallet:<lowercaseAddress>` is accepted as an opaque stored account binding.

Usage order: `prepareCustomer` → `store.saveUnsigned(scope,id,unsigned)` → browser signs `unsigned.typedData` and the exact separate Stellar approval digest → root verifies/persists customer approval → root reloads unsigned → `authorizeCustomer` → `store.saveSigned(scope,id,signed,hash(signed.payload))` → explicit `send(signed)`. Both Stellar and EVM approvals must bind the same immutable intent. Existing provider eligibility/funding callbacks remain mandatory and are not inferred from a configured wallet or a browser boolean. They do **not** require a prior successful order; root checks current attributable funding, account and access policy. Read-only reconciliation remains available after expiry and never resends.

`HyperliquidTestnetHttpTransport({fetch?,now?}={})` is exported for explicit root construction. Construction makes zero requests. It accepts only the exact fixed Testnet RPC/info/exchange URLs and allowlisted read requests/single IOC order shape. Each explicit call uses a15-second abort/race deadline, redirect:error, no-store, JSON content type,64KiB request cap and1MiB streamed response cap (including missing/dishonest content-length). Redirected/wrong final URLs, nonJSON, oversized/malformed/error responses and thrown transport details become a sanitized shared error without provider body/credentials. There is no automatic follow-up broadcast, retry or leverage change. Tests inject fetch; no live exchange request was performed.

Validation for this extension: **77 offline tests passed** (61 adapter/browser tests plus16 transport tests), full API typecheck and secret scan passed. New cases prove unsigned serialization/no signer/no premature approval check, customer wrong-domain/source signature rejection, immutable typed data/nonce/action/account/baseline, expiry and changed current position/leverage, missing account proof, exact signed persistence, strict endpoints/verbs/action shapes, response/body caps, timeout/no retry and sanitization. Financial acceptance remains unverified and blocked by the root's configured provider-access/funding gates.
